# depot

The per-database Depot engine. FDB is the authoritative store. LTX V3 file format throughout.

For implementation-level wiring (key encodings, RTT count for `commit`, LTX byte layout, compaction shard rules, test harness setup) see the `## Depot tests` and `## Pegboard Envoy` sections in `engine/CLAUDE.md`. The bullets here are the **architectural constraints** that shape what does and does not belong in this package.

## Hard constraints (binding floor)

These come from `r2-prior-art/.agent/research/sqlite/requirements.md` and supersede any contradiction in older specs.

- **Single writer per database.** Pegboard exclusivity (lost-timeout + ping protocol) holds. Never two writers on the same database at the same instant. Do not implement MVCC, page-versioned read-set tracking, optimistic conflict detection at commit, content-addressed dedup, or commit-intent logs. mvSQLite's PLCC / DLCC / MPC / versionstamps are explicitly out — single writer makes them dead weight.
- **No local SQLite files. Ever.** Not on disk, not on tmpfs, not as a hydrated cache file. The authoritative store is FDB. The VFS speaks to it directly. Forks do not materialize local files. Anything that puts a real SQLite file on a pegboard node is out of scope.
- **Lazy read only.** No bulk pre-load at database open. Pages are fetched on demand from the hot tier. The per-WS-conn PIDX cache + flattened ancestry cache amortize the per-fetch cost. Fork warmup is a *background* copy, not a synchronous bulk hydrate at first SQL statement.
- **Per-commit granularity.** The smallest addressable unit is a committed transaction. No sub-commit PITR, no WAL-frame-level shipping.

## Statelessness contract

- **The hot path (pegboard-envoy → Db) is pod-stateless.** Every request self-describes its fence (branch_id, expected generation/head_txid in debug) and runs against the current FDB state. In-memory state on `Db` is allowed only as a **perf cache** — never as the source of truth, never as a correctness fence, never as something that must survive across requests. WS conn drop = cache drop. No `open` / `close` lifecycle.
- **Workflow compaction is the only compaction authority.** Do not reintroduce standalone hot or eviction compactor modules or tests.
- **Pegboard-envoy WS conn is stateless w.r.t. database identity.** Envoys can reconnect to a different worker mid-flight while a database is active; the new worker never sees the original actor start command. The only per-conn state is the perf-only `scc::HashMap<database_id, Arc<Db>>`, populated lazily by SQLite request handlers. No active-database registry, no presence tracking, no start handler. Stop only evicts the cache entry.
- **Defensive runtime checks for "this should never happen" are `#[cfg(debug_assertions)]` only.** Trust the surrounding contracts (pegboard exclusivity, FDB tx isolation, workflow uniqueness). Belt-and-suspenders fences that duplicate work the surrounding system already does belong in debug builds, not in release.

## Concurrency model

- **Pegboard exclusivity is the only writer fence in release.** No separate KV concurrency fence. Defensive in-tx "two writers detected" checks are `#[cfg(debug_assertions)]` only.
- **The DB manager workflow owns compaction publish and deletion authority.** Hot and reclaimer companions self-plan and drain their full backlog in an internal durable `loope`, then signal the manager once; the manager installs/publishes the merged output, advancing the watermark and bumping the manifest generation a single time.
- **PIDX deletes use FDB `COMPARE_AND_CLEAR`** so commit-vs-compaction races no-op on stale entries. Takes no read conflict range.
- **A byte budget is not chunking. Every scan-and-mutate pass commits per chunk behind a cursor.** Bounding a transaction's bytes bounds what one attempt reads; it does not bound what a failure costs. A pass that derives a whole candidate set and then mutates it in a single transaction is all-or-nothing under OCC, so any conflict discards the entire batch, the next attempt re-reads it from the start, and none of that read volume is visible to anything measuring commits. Chunk size and commit granularity must be the same unit: derive and mutate one bounded window inside one transaction, advance a cursor, and hold cross-chunk context in local activity memory rather than workflow state (`SweepDeadShardVersions`, `SweepStalePidx`). Deriving in one transaction and mutating in another forces the mutator to re-derive the whole set and reject on any mismatch, which doubles the read volume and turns every race into discarded work; split the two only across a real phase boundary (hot staging then install), never merely because planning happens in a different activity. The reclaim commit/delta lane was the counterexample: capped at `CMP_FDB_BATCH_MAX_KEYS` / `CMP_FDB_BATCH_MAX_VALUE_BYTES` and still the cluster's largest FDB reader, because the cap applied per attempt and the pass frequently never committed.
- **Fork-vs-GC race is OCC, not margin-based.** Database fork derivation regular-reads the parent `restore_point_pin` and `depot::gc::read_branch_gc_pin_tx` inside the fork tx; concurrent GC pin advance aborts the fork via OCC. Hand-waved time margins are not a substitute.
- **Compaction load is bounded by the UniversalDB throttle, not by depot code.** Every bulk background transaction opts in with `tx.charge_throttle(DEPOT_COMPACTION_THROTTLE, ...)` at the top of its body and UniversalDB charges what it reads and writes. Reads are charged as they happen and for every attempt, including ones that never commit; writes once, only on commit. Never hand-derive a charge from a pass's `CompactionBatchBudget` `value_bytes()`: that counts only rows that reached the candidate set, so the pins, retained PITR interval rows, bucket fork proofs, PIDX ownership probes, and every row a scan reads then rejects become free. The candidate set is capped at a couple of megabytes while those scans grow with the branch, so a derived charge understates real load by more the bigger the database gets, which is backwards.
- **Two axes, one budget each, scoped by whether a read moves bulk data in the background.** The write axis (`compaction_write_bytes_per_second`, default 16 MiB/s) bounds what hot compaction and reclaim write; the read axis (`compaction_read_bytes_per_second`, default 64 MiB/s) bounds what the bulk readers pull. Gating happens before the heavy read in each pass: hot stage/install before `read_hot_input_snapshot`, and both the reclaim plan scan and the delete-side re-derive. The bulk sweeps (dead-shard versions, staging repair cleanup) and the stale-PIDX walk charge without gating: they delete as they go behind cursors, so charging is enough to make other work yield without adding a stall mid-repair. Actor-facing reads and operator paths (`doctor`, `recovery`, `inspect`) stay off the axes entirely; throttling a live query to protect background compaction inverts the priority.
- **A range clear must report its own volume.** Automatic write bytes cover what an operation submits, which is the whole cost of a `set` or a `COMPARE_AND_CLEAR` (it carries the value it clears) but not of a `clear_range`, which submits two keys and removes an unbounded amount. Report the removed volume with `tx.charge_throttle_bytes(...)`.
- **The throttle classes order callers by what they do to the FoundationDB footprint: `Stage` < `Install` < `Reclaim`.** Every class charges one counter, so cluster volume stays on one budget and the class only scales the budget its own admission ramp is evaluated against; ordering the budgets is what orders the callers. Membership is by effect, not by lane: `Stage` is only hot staging that writes a second copy (the fold lands in STAGE and install copies it into SHARD byte for byte), so it is gated well below the configured rate. `Install` covers everything that advances without duplicating, including hot folds under `compaction_hot_fold_direct_to_shard` (the image is written once); pick that one with `throttle::hot_slice_class`, never by naming a variant at a hot-slice call site. `Reclaim` sits above the configured rate and is the only class that does, so it alone bounds how far peak pressure can exceed it. Without the ordering a backlog pins the estimate just under budget and new data is staged as fast as stale data is installed and deleted, so the branch's footprint never comes down. Every multiplier and soft mark is runtime-configurable under `sqlite.compaction_*_throttle_*`, and a duplicating staging slice additionally backs off for `sqlite.compaction_stage_throttle_backoff_ms` (much longer than `THROTTLE_BACKOFF_MS`) so its retries stop competing for the budget the other callers are working under.
- **Compaction start is gated by percentage-based admission (`compaction_admission_percent`, default 100).** The DB manager refresh hashes the branch id to a stable bucket and, if outside the admitted fraction, starts no hot or reclaim job for that branch while still tracking its backlog. Decided fresh every refresh (in the `RefreshManager` activity, never the workflow body, so config reads stay replay-safe), so raising the percent lets a skipped branch compact on its next check. Explicit force-compaction requests bypass the gate.

## Storage layout

- **All PITR database state is per-branch.** Db resolves DBPTR, caches the branch id as a perf cache, and writes hot-path data under top-level `[0x02][0x30]/{branch_id}/<suffix>` keys.
- **Db is bucket-scoped.** New Db instances receive the engine namespace id as a Depot bucket id, lazily seed BUCKET_PTR/BUCKET_BRANCH, and write DBPTR under the resolved bucket branch.
- **Database pointer resolution walks bucket branch parents on DBPTR miss.** Bucket-branch tombstones return `DatabaseNotFound` and must not fall back to legacy database-scoped storage.
- **Db branch and PIDX caches must be invalidated when DBPTR moves.** Rollback swaps can make cached branch id, quota, and PIDX rows stale; resolve DBPTR as the source of truth before using cached branch-local state.
- **Db async perf caches use async-safe primitives.** Use `tokio::sync::RwLock` for mutable cache snapshots, keep `DeltaPageIndex` unwrapped because its `scc::HashMap` owns concurrency, and use atomics for synchronous metering snapshots.
- **Db branch read caches publish atomically.** Keep branch id, ancestry, access bucket, and PIDX index in one `CacheSnapshot` under `cache_snapshot`.
- **Debug-only `Db` constructor reconciliation must stay non-blocking.** Schedule takeover reconcile on the current Tokio runtime or a detached background thread; never join it from `Db::new*`.
- **Legacy database-scoped storage is not a read fallback.** Db reads use branch-scoped META, COMMITS, VTX, PIDX, DELTA, and SHARD keys.
- **Legacy database-scoped key helpers are v1 pegboard compatibility only.** Do not use `meta_head_key`, `delta_prefix`, `pidx_delta_prefix`, or `shard_prefix` for current Depot invariant scans.
- **Branch ancestry reads use branch-aware sources.** The PIDX cache is safe only when the read plan has one source branch; multi-branch ancestry reads must scan PIDX with branch identity.
- **Flattened ancestry caches store versionstamp caps.** Resolve cached parent versionstamps to txids inside each read transaction before PIDX/SHARD lookup.
- **Ancestor PIDX reads are capped by fork point.** Ignore PIDX owners newer than that source's cap, scan capped DELTA history for requested pages, then fall through to the latest SHARD version at or below the cap.
- **The capped DELTA-history walk is floored by `min(latest SHARD version <= cap, CMP/root.hot_watermark_txid)` per shard.** A folded version is a complete image of its shard, so it supersedes every delta of that source at or below it; the walk reads only above that floor and stops searching a page once it descends past it. Without the floor, a page already folded (its PIDX row cleared) is in no retained delta, so the walk runs the source's whole retained history on every read before SHARD gets a turn, bounded only by reclaim lag and PITR pins. The watermark term is load-bearing: it is what licenses clearing a folded page's PIDX row, so a version above it (half-installed or hand-written) must yield no floor. The floor is per source, so a page one source's shard covers still reaches the next source.
- **Workflow compaction read fallback preserves hot-tier order.** PIDX/DELTA wins and branch SHARD fallback is next.
- **Conveyer read domains live behind the `conveyer/read.rs` facade.** Keep read planning, PIDX/cache helpers, SHARD fallback, and transaction scan helpers under `conveyer/read/*.rs`.
- **Sparse in-range reads zero-fill only when no source exists.** Corrupted or broken source blobs must return an explicit read error, not a zero page.
- **PIDX-owned DELTA gaps are broken source coverage.** Missing delta chunks may fall back only to valid SHARD coverage; otherwise return `ShardCoverageMissing` or a decode error.
- **Read-path tests should seed branch-owned storage.** Use `Db::commit` or `BR/{branch}` keys, not pre-PITR database-scoped `META`/`PIDX`/`DELTA`/`SHARD` keys.
- **Conveyer branch domains live behind the `conveyer/branch.rs` facade.** Keep branch resolution, bucket catalog/list/delete, fork/derive, lifecycle rollback, and shared branch helpers under `conveyer/branch/*.rs`.
- **Conveyer commit domains live behind the `conveyer/commit.rs` facade.** Keep commit apply, branch initialization, dirty-marker signaling, truncate cleanup, and transaction helpers under `conveyer/commit/*.rs`.
- **Reads must fail on cold-only coverage.** A branch carried over from an enterprise build can still hold `CMP/cold_shard` rows whose objects are unreachable here. If a read finds one and nothing else covers the page, return `ShardCoverageMissing` instead of zero-filled bytes.
- **Shard-cache fill workers use cloned `async-channel` receivers.** Do not reintroduce a shared `Mutex<mpsc::Receiver>` around worker dispatch.
- **Shard-cache fill idle waits pre-arm `Notify` before checking `outstanding`.** `notify_waiters()` does not store permits.
- **Shard-cache metrics use fixed outcome labels only.** Keep branch, database, shard, object, restore point, and bucket identifiers out of metric labels.
- **Truncate cleanup prunes the boundary SHARD instead of blindly deleting it.** `shard_id = pgno / SHARD_SIZE`, so page 64 and page 65 both map to shard 1.
- **Debug historical reads cannot trust PIDX.** PIDX is the current owner map, so `debug::read_at` scans DELTA history up to the target txid before falling through to SHARD layers.
- **Fresh fork branches use `/META/head_at_fork` until first commit.** The first local commit treats it as the previous `DBHead`, writes `/META/head`, and clears `/META/head_at_fork` in the same transaction.
- **PITR tunable constants live in `conveyer/constants.rs`.** Import shared limits and retention windows from there instead of duplicating literals.
- **PITR and shard cache policy storage lives in `conveyer/policy.rs`.** Payloads live in `conveyer/types/policy.rs`; database overrides fall back to bucket policies, then defaults. The default `PitrPolicy` comes from the global Rivet config (`sqlite.pitr`) through `PitrPolicy::from_config`, so read paths take it as a parameter instead of a const.
- **PITR is opt-in and off by default (`sqlite.pitr` absent).** `PitrPolicy::from_config` returns `Option`, and a disabled cluster selects no interval coverage and ignores stored bucket/database overrides rather than falling back to them; overrides stay written so re-enabling restores them. Every retained coverage position makes hot staging fold a complete image of each shard it covers, so live shard versions scale with `retention_ms / interval_ms` and enabling PITR is a deliberate FDB-footprint trade.
- **PITR interval coverage storage lives in `conveyer/pitr_interval.rs`.** Payloads live in `conveyer/types/compaction.rs`, and branch-local keys use `BR/{branch}/PITR_INTERVAL/{bucket_start_ms_be}`.
- **Restore-point creation must re-read the target `COMMITS/{txid}` row in the pin-write transaction.** Missing history aborts with `RestoreTargetExpired`; never write a Ready pin for deleted history.
- **Workflow compaction key helpers live in `conveyer/keys.rs`.** Branch-local manifest/staging keys stay under `BR/{branch_id}/CMP`, while global pin/proof/dirty indexes use reserved partitions `0x70..=0x75`.
- **Every `DBPTR` write goes through `branch::write_database_pointer`, which also writes the `DB_BRANCH_OWNER` (0x77) reverse index row.** Compaction resolves a branch's `(bucket, database_id)` policy scope from that single point read; the fallback DBPTR scan reads every database in the cluster, so it must stay a one-time per-branch seed and never a steady-state path. A pointer swap clears the superseded branch's owner row.
- **The owner row records `bucket_id` rather than deriving it from the bucket branch.** Walking a bucket branch to its root and matching the bucket whose pointer equals that root is ambiguous: a rolled-back bucket points at a descendant of its root (matching nothing), and a forked bucket shares its source's root (matching the source). Do not reintroduce that derivation on the read path.
- **Workflow compaction signal and durable state contracts live in `compaction/types.rs`.** Keep them serde-compatible for Gasoline runtime use; do not add vbare helpers unless they become persisted or BARE wire payloads.
- **Workflow compaction uses one module per workflow.** Keep `DbManagerWorkflow`, `DbHotCompactorWorkflow`, and `DbReclaimerWorkflow` in `workflows/{db_manager,db_hot_compactor,db_reclaimer}.rs`; shared helpers live under `compaction/`.
- **Workflow compaction input fingerprints use SHA-256 over length-prefixed chunks.** Preserve the existing field order when adding fingerprint inputs. The reclaim fingerprint commits both sides to deriving byte-identical scanned windows, not merely identical candidate sets: the commit/delta lane contributes four fields (`delta_reclaim_txids`, `commit_reclaim_txids`, and the whole scanned `commits` and `delta_chunks`). A slice that does not own that lane must therefore exclude all four through `fingerprint_reclaim_inputs_scoped`, with the same flag on the planning and delete sides. Excluding only the txid lists leaves the deriving side hashing a populated window against an empty one, which fails every slice with `reclaim input fingerprint changed`; because the drain is gated on `!is_repair && status == Succeeded`, that silently disables the drain and the manager re-dispatches in a loop rather than reporting anything.
- **Workflow compaction branch workflows use `DATABASE_BRANCH_ID_TAG` as their only stable unique tag.** The manager stores required companion workflow ids before entering its durable loop.
- **Workflow compaction manager input may carry actor context for logs.** Keep workflow uniqueness branch-only, and pass runtime actor ids through `DbManagerInput.actor_id` when available.
- **Workflow compaction jobs carry the database branch lifecycle generation.** Stage, publish, and reclaim activities must reject stale work when the branch record is missing, frozen, or generation-changed.
- **The manager must always leave a wake deadline armed.** Only commits signal it, so an iteration that receives no signal falls back to the `sqlite.manager_idle_poll_interval_ms` poll (jittered by a stable hash of the branch id, since it is computed in a replayed workflow body). A parked manager strands every reclaim lane: shard-cache eviction, the dead-shard sweep, expired `PITR_INTERVAL` cleanup, and the one-shot `SweepStalePidx` repair. Do not make reads signal the manager instead.
- **Workflow compaction manager planning runs through `RefreshManager` activities.** Recompute branch lag from FDB, record one active job in durable state, then signal the persistent companion workflow.
- **Workflow compaction planned jobs use typed lanes.** `RefreshManagerOutput` carries concrete hot and reclaim planned-job structs; dispatch helpers should not unpack a generic input-range enum.
- **Workflow compaction manager active jobs use typed lanes.** Store dispatched hot and reclaim work under `DbManagerState.active_jobs` with concrete input ranges.
- **Workflow compaction manager stops use explicit reasons.** Store stop requests as `ManagerStopReason` and route explicit destroy plus branch-not-live refresh through the shared stop effect.
- **Workflow compaction manager helpers orchestrate only.** Keep FDB snapshots and UDB writes inside activities.
- **Workflow compaction manager orchestration is effect-driven.** Signal and refresh helpers emit `ManagerEffect` values; the executor owns workflow API calls, activities, timestamps, and signal dispatch.
- **Workflow compaction joined signals expose `database_branch_id()`.** Manager and companion loops should filter unrelated branch signals once before variant-specific handling.
- **Workflow companion signal handlers are kind-specific.** Hot and reclaim loops choose typed signal handlers first; storage work stays inside activities.
- **Workflow force-compaction state lives in `ForceCompactionTracker`.** Manager code should use tracker methods for request, result, attempted-job, and completed-job bookkeeping.
- **Workflow force-compaction tests use `DepotCompactionTestDriver` under `depot/test-faults`.** Wait on durable `force_compactions.recent_results`, not planner deadlines or arbitrary timing thresholds.
- **Workflow fault-hook tests should assert durable forced results.** Manager retries can surface a terminal error and still settle later state in the same forced cycle.
- **Nothing that scales with database size, history length, or shard count may cross a gasoline boundary.** Durable `loope` state, signal bodies, and activity inputs/outputs carry only fixed-size scalars: cursors, job ids, watermarks, generations, versionstamps, fingerprints, and counts. Page bytes, LTX blobs, ref lists, and per-shard maps stay transaction-local or in local activity memory, and anything a later step needs is re-derived from FDB (staging sidecars scanned by job id, or a re-read from a persisted cursor). A growing collection in workflow state is persisted several times over per pass and eventually exceeds the FDB transaction limit, which wedges the workflow so it can no longer run or replay. When a step needs more data than one bounded window holds, add a scalar cursor and sweep, never an accumulator.
- **Workflow compaction drains a bounded txid window per job.** `plan_hot_job` caps `drain_head_txid` at `hot_watermark + MAX_HOT_DRAIN_SPAN_TXIDS` (raised to the first fold so oversized folds still drain); the manager loop catches a large backlog up incrementally across refresh cycles. Never reintroduce an unbounded `head.head_txid` / `hot_watermark_txid` drain span.
- **Workflow hot compaction writes staged LTX blobs under `CMP/stage/{job_id}/hot_shard` plus a ref sidecar row per staged shard under `CMP/stage/{job_id}/hot_ref/{min_txid}/{shard_id}/{as_of_txid}`.** The hot companion drains every slice in `[hot_watermark+1 .. H0]` internally, pinning the drain-start head `H0` and PITR clock `T0` so all slices bind the same inputs. Companion loop state and the `HotJobFinished` signal carry only the cursor/job id, never the ref list; the manager install re-derives each chunk's refs by scanning the `hot_ref` sidecar for `min_txid == cursor`. Never accumulate the merged ref set in workflow state or signals (that grew Gasoline state past the FDB txn limit and wedged the workflow).
- **Hot stage write volume is not bounded by its input read budget, so each stage transaction stops at `CMP_STAGE_MAX_WRITE_BYTES` and resumes from a `(as_of_txid, shard_id)` cursor.** Staging folds a complete shard image per `(coverage txid, touched shard)` pair, so a slice scattered across many shards (or one wide commit) writes far more than it read and would exceed FDB's transaction limit. The activity plans and reads the fold inputs in one transaction, holds the decoded inputs in local memory, and stages them across bounded write transactions; the cap is checked before each image so every transaction writes at least one and the drain cannot stall. The companion holds its txid cursor until staging reports no next cursor.
- **Hot install write volume is not bounded by its chunk boundaries either, so each install transaction stops at `CMP_INSTALL_MAX_WRITE_BYTES` and resumes from a `(shard_id, as_of_txid)` cursor.** A chunk copies each staged image into the live SHARD tier byte for byte, so it writes what staging wrote for that chunk, and staging spreads an oversized chunk over many transactions. The chunk's PIDX clears, fold-index rows, and PITR coverage land only in the transaction that finishes its copies, so a partially copied chunk publishes nothing. Do not count a job's staged refs to report installed shards; that scan spans the whole drain. Accumulate the count across activity calls instead.
- **Workflow hot install runs in the DB manager as a resumable bulk activity.** It re-derives the drain's budget chunks via a cursor, copying staged shards and clearing PIDX per FDB transaction without touching the manifest, then advances `CMP/root.hot_watermark_txid` to `H0` and bumps the generation once in a final transaction. An activity call that crosses `CMP_BULK_ACTIVITY_EARLY_TIMEOUT` returns the cursor and the manager re-dispatches from it, so the hard activity timeout never has to cover the whole window. COMMITS are never cleared here, so chunk boundaries stay stable and the whole install is idempotent across retries (content-addressed shard copies, `COMPARE_AND_CLEAR` PIDX clears). Correlation is by job_id plus base manifest generation, not a per-slice fingerprint.
- **Every written hot SHARD version must be a complete image of its shard at its `as_of_txid`.** Reads resolve a page from exactly one shard version and zero-fill whatever that version is missing, so a sparse version silently corrupts the database. The fold merge base must therefore consider the job's own `CMP/stage/{job_id}/hot_shard` rows and not just installed `SHARD` rows: a drain stages every slice before the manager installs any of them, so a later slice folding a shard cannot see the earlier slice's image for that shard. Both merge-base sources are FDB-only, which is the whole store here.
- **Workflow hot planning treats `DB_PIN` records as exact coverage targets.** Preserve pinned txids in `HotJobInputRange.coverage_txids`; do not round them up to the latest head.
- **Workflow hot planning treats selected PITR intervals as exact coverage targets.** Include selected interval txids in coverage fingerprints and publish their `PITR_INTERVAL` rows during hot install.
- **Workflow FDB reclaim is manager-planned and reclaimer-executed, except the commit/delta lane, which derives and clears itself.** For the shard-cache lane: recompute DB pins, PIDX dependencies, and SHARD coverage before signaling the reclaimer, then revalidate them in the delete activity and clear hot rows with `COMPARE_AND_CLEAR`. The commit/delta lane instead runs in `SweepCommitDeltaChunk`, which derives one budget-bounded `COMMITS`/`DELTA` window and clears it inside the same transaction, advancing `ReclaimDrainState.commit_scan_cursor` by committing rather than by planning. That lane had no phase boundary to justify a split: nothing downstream consumes its candidate set, so the plan/delete pair only bought a second full scan of the history plus a rejection path, and it made the delete the cluster's largest FDB reader. With derive and clear in one transaction the `Serializable` reads are themselves the fence, so there is no set to compare.
- **The reclaim drain is versioned per job, never per workflow.** `run_reclaim_job` selects v1 or v2 with `match ctx.check_version(2).await?`, following `pegboard/src/workflows/actor/mod.rs`. The check MUST stay inside the per-signal handler: the reclaim companion is a persistent `lupe` that never completes, so a check at the top of the workflow would pin every branch that already has a companion to v1 for the life of the branch, and the new drain would only ever reach branches created after it shipped. Inside the handler, a job already mid-drain finishes on v1 and the branch's next job records v2. `run_reclaim_drain_v1` is frozen: it is reached only by jobs whose version check recorded `1`, it will realistically never be deleted, and nothing new belongs in it.
- **A settled branch occupies ~1x its logical size.** There is no designed steady-state multiple; do not explain an undraining branch with one. Retained DELTA below `hot_watermark_txid` means stale PIDX ownership. Probes are in `docs-internal/engine/sqlite/compaction-flow.md`.
- **Workflow FDB reclaim treats unexpired `PITR_INTERVAL` rows as soft pins.** Expired interval rows are reclaim inputs and must be compare-cleared with the planned value.
- **Workflow reclaim commit scans are bounded by exact `branch_commit_key` ranges.** Do not full-scan `branch_commit_prefix` and locally filter high txids.
- **Windowed reclaim scans advance a cursor across drain passes; an empty plan is never a terminal condition.** The commit/delta lane (`commit_scan_cursor`) walks its range in budget-bounded windows, and every scanned row is charged against the budget whether or not it is reclaimable. A scan that restarts at the beginning each pass spends the whole window on retained rows and reports "nothing reclaimable" forever, stranding the history behind them. The drain stops only when the scan reports its range exhausted (`commit_scan_complete`) or the slice is rejected, never on `planned: None` alone. In v2 the sweep reports `commit_scan_complete`, and the plan is passed `skip_commit_delta` so it does not scan the same window a second time, including for the entry slice the manager plans before the drain's version check.
- **Workflow reclaim slices share one `CompactionBatchBudget` across all delete lanes.** Every delete candidate (expired PITR rows, shard-cache demotes, and in v1 commits/deltas) counts its keys and value bytes against the shared budget because `COMPARE_AND_CLEAR` carries the compared value into the single slice transaction; plan and delete consume the budget in the same order so both derive identical sets, and capped tails drain across later slices. The dead-shard version-retention sweep (C4) is NOT a lane here, and in v2 neither is commit/delta: `SweepCommitDeltaChunk` owns its own budget per chunk, and clears the expired PITR rows it already read to build its retention set.
- **The stale-PIDX repair sweep runs in the standalone `SweepStalePidx` activity and is one-shot per branch.** It clears rows a hot slice folded but left PIDX-owned, which the owner-window filter in `read_hot_input_snapshot` can never revisit and which therefore pin their `DELTA` and `COMMITS` rows forever. It carries a persisted `pgno_cursor` (unlike the dead-shard sweep, which re-walks from the start) because a retained row stays in place, so a restart would re-read every live PIDX row before reaching the next stale one. Completing the walk writes `CMP/pidx_repair`, which retires the sweep; without that marker it would re-scan the whole prefix on every reclaim job for nothing. A sweep at `hot_watermark_txid == 0` returns before walking and leaves the marker unwritten, because no fold has installed yet so no row can classify stale and retiring there would spend the one-shot marker on a walk that inspected nothing. Clearing requires a `SHARD` version at or above the owner txid whose image actually carries the page, not merely a version that exists in that range: a fold stages only pages whose PIDX owner falls inside its slice window, so a shard accumulates versions that omit a page written before that window, and clearing on existence alone drops the page's only pointer. Fail closed and retain otherwise.
- **Dead-shard version retention (C4) runs in the standalone `SweepDeadShardVersions` activity, not as a reclaim-slice lane.** It walks the whole `CMP/fold` index chunk by chunk in its own bounded FDB transactions, carrying the cross-chunk supersession context (`prev`, the last fold txid per shard) in LOCAL activity memory, and deletes each chunk's dead versions (clear rows, credit quota, drop the shard from its `CMP/fold` entry) in the same transaction that found them, so no plan/delete OCC fence is needed. Never persist `prev` through workflow state (loope state or activity I/O): it is O(live shard count) and grew Gasoline state past the FDB txn limit on large branches. A single forward walk detects every current supersession, so the activity finishes in one call unless it crosses `CMP_BULK_ACTIVITY_EARLY_TIMEOUT`, in which case it returns `Requested` and the companion re-dispatches (re-walking from the start, which skips already-deleted versions). The manager triggers the reclaim job whose companion runs this sweep via a bounded first-chunk `dead_shard_sweep_needed` check; the sweep uses its own budget per chunk.
- **Workflow FDB reclaim resolves bucket fork facts before deletion.** Treat missing or ambiguous `BUCKET_FORK_PIN`/`BUCKET_CHILD` proof as a retention blocker, and materialize exact `DB_PIN(kind=BucketFork)` records before planning reclaim.
- **Workflow repair cleanup runs through the lifecycle-fenced reclaimer.** Stale hot completions clear exact staged FDB rows.
- **Compaction cleanup re-derives refs from the staging area by job id, never from a carried list.** Failed hot installs schedule a reclaim job carrying `stale_hot_job_ids`. The reclaimer scans `CMP/stage/{job_id}/hot_ref` to find the orphan blobs. Hot staged rows are not cleared on a successful install (same lifecycle as the staged blobs).
- **A cleanup request the manager cannot dispatch is queued, never dropped.** The job id lives nowhere but the request, so a drop leaks that job's whole staging area. `DbManagerState.pending_cleanups` holds the deferred ids (bounded by `CMP_MAX_PENDING_CLEANUP_JOB_IDS`) and the next free reclaim slot dispatches all of them as one merged repair job, ahead of any planned reclaim work. A finished repair job's ids stop being excluded from the staging scan, so the scan re-reports whatever it failed to clear one refresh later; do not re-queue them directly, which retries a deterministic rejection every iteration with nothing rate-limiting it. Cleanup outranks planned reclaim but yields the slot every other cycle when reclaim work is also ready, so a cleanup that keeps failing cannot stop the reclaim lanes. Never add a drop path here: the reclaimer is normally busy right when a cleanup request arrives, so the drop path is the common path.
- **The manager refresh scans `CMP/stage/` for job subspaces belonging to no in-flight job and feeds them back through the same cleanup lane.** This is the backstop for ids the queue refused or a lost manager generation forgot, and the only thing that collects staging stranded before the queue existed. It reads one row per job subspace and skips past the rest, so it must never enumerate staged rows.
- **Staging cleanup clears as it goes, so its walk is self-advancing.** Hot cleanup clears each staged ref row it handles, so re-dispatching the same input resumes where it stopped and it only needs `has_more`; a job with no ref rows left has its whole subspace cleared, since blobs and their ref row are staged in one transaction. Every cleanup path must terminate: a staged shard whose bytes no longer match its ref is cleared with a loud log rather than retained, because retaining leaves the ref row that makes the staging scan re-report that job forever. `compare_and_clear` is what keeps that safe against a concurrent writer.
- **Workflow compaction wakeups are injected into `Db` as a signaler.** The commit path owns `SQLITE_CMP_DIRTY` admission, while runtime callers decide how to create or target the unique manager workflow.
- **Dirty-marker cleanup proves idle from workflow `CMP/root`.** Do not use legacy `/META/compact` materialized txid as a fallback.
- **`Db` constructors do not take UPS.** Keep workflow wakeups behind `CompactionSignaler`; do not reintroduce legacy compactor PubSub wiring.
- **Truncate cleanup fences observed PIDX and SHARD values before writing.** Snapshot-selected rows must be re-read with Serializable isolation before cleanup clears or rewrites them so concurrent workflow output cannot be clobbered and quota accounting retries cleanly.
- **UDB helper scans return logical conveyer keys.** Apply the supplied `Subspace` to the physical range scan, then strip it before returning rows to callers.
- **Depot inspect decode and pagination logic lives in `depot::inspect`.** `api-peer` should only mount thin internal `/depot/inspect/...` handlers and must not expose this surface through public SDKs.
- **Depot inspect scans are bounded by an explicit `ScanBudget` and report truncation; over-cap limits clamp rather than error.** A branch blob runs eleven scans in one FDB transaction, so each budget is per consumer (row families share one, each probe gets its own) and never per prefix. Take footprint from `get_estimated_range_size_bytes`, which takes no scan, not from summing scanned rows. A silently empty or silently capped answer reads as "clean" and has already caused wrong conclusions twice.
- **`CMP/reclaim_progress` is diagnostic output only.** The reclaim plan transaction writes it after its liveness and generation guards; nothing reads it back into planning.
- **Conveyer persisted payload structs use `serde::{Serialize, Deserialize}` as the serde_bare/vbare-compatible derive pattern.** Add `OwnedVersionedData` wrappers when introducing encode/decode helpers.
- **Conveyer type domains live behind the `conveyer/types.rs` facade.** Add branch, restore_point, compaction, history-pin, storage, page, and id payloads under `conveyer/types/*.rs` and re-export public names from the facade.
- **META splits into single-writer sub-keys:** `/META/head` (commit-owned), `/META/quota` (atomic-add counter, raw i64 LE, not vbare), and workflow `CMP/root` (manager-owned compaction manifest).
- **Access-touch uses manifest sub-keys only.** Route commit/read touches through `touch_access_if_bucket_advanced`; do not enqueue the legacy eviction index.
- **Burst-mode quota uses FDB-derived branch lag.** Route hot quota cap decisions through `depot::burst_mode`; do not add per-pod tier gates.
- **Legacy eviction helpers are removed.** Workflow reclaimer planning owns deletion eligibility from current manifest, pins, PIDX, and SHARD.
- **`COMMITS/{txid_be}` stores `CommitRow` via `SetVersionstampedValue`; `VTX/{versionstamp}` is written via `SetVersionstampedKey` and maps to raw u64 BE txid.**
- **Hot retention clears `COMMITS` and matching `VTX` rows together.** Do this inside the hot compactor write tx and keep quota accounting paired with the cleared keys.
- **Branch records live under `[BRANCHES]/list/{branch_id}` with FDB atomic-add refcount plus `desc_pin` and `restore_point_pin` atomic-min keys.** GC reads these scalars instead of walking the descendant tree.
- **Database branch records are current-only vbare payloads.** Do not add legacy decode paths that default missing `lifecycle_generation`.
- **Sweeping a forked database branch releases the parent fork retention.** Delete the parent `DB_PIN(kind=DatabaseFork)`, recompute `desc_pin`, and decrement the parent refcount in the sweep transaction.
- **Empty `restore_point_pin` state is key absence, not `[0; 16]`.** Clear `branches_restore_point_pin_key` when deleting the last restore point so a later `MutationType::ByteMin` can initialize from the next real versionstamp.
- **Branch GC pin computation lives in `depot::gc`.** Use it for hot-history cleanup and debug estimates instead of duplicating refcount/root/desc/restore point pin math.
- **Bucket catalog entries store branch ids with 16-byte versionstamped values.** `list_databases` walks bucket parents, caps inherited BUCKET_CATALOG rows by `parent_versionstamp`, and lets database tombstones mask inherited visibility.
- **Database tombstones store 16-byte versionstamped values.** `list_databases` applies the same bucket parent cap to tombstones so deletions after a bucket fork do not hide databases in the older fork.
- **Branch pin atomic-min writes use `MutationType::ByteMin`** because versionstamps are 16-byte lexicographic big-endian values.
- **PITR, forking, and `restore_database` are all the same primitive: branch-at-position.** PITR creates a new branch at the resolved restore point; the broader system (pegboard) decides whether to swap the database's head pointer onto it.
- **`MAX_FORK_DEPTH = 16`.** Deeper trees indicate misuse.

## History retention

- **GC is a dependency-graph walk, not a wall-clock cutoff.** A layer is deletable only when older than `PITR_WINDOW_MS` AND not pinned by any descendant branch's fork point. No monotonic ratchet on `retention_pin_txid` — pin recomputes per pass, decreases when descendants delete.
- **Frozen branches use `created_at_ms`-based retention, not `head_txid - window`.** Their `head_txid` is fixed; window math against it would drift forward and GC their history out from under live descendants.

## Restore Points

- **Restore point wire format is 33-char `{timestamp_ms_hex_be:016}-{txid_hex_be:016}`.** Branch identity is not in the wire format.
- **Restore points are retained `RestorePointRecord` rows.** Do not add non-retained restore point create or resolve fallback paths.
- **Conveyer records carry restore points as `RestorePointId`, not raw `String`.** The wrapper validates the 33-character ASCII wire format at construction and decode.
- **Use `RestorePointId::format(ts_ms, txid)` and `RestorePointId::parse()`** instead of hand-formatting or slicing restore point strings.
- **Restore point creation is FDB-only.** `PinStatus::Ready` means `DB_PIN(kind=RestorePoint)` exists, and current records keep `pin_object_key: None`.
- **Restore point creation resolves `SnapshotSelector` first.** Persist the exact resolved txid/versionstamp as the restore point record and `DB_PIN`; do not mint retained tokens from caller-supplied timestamps.
- **Restore point deletion removes the restore point key, deletes `DB_PIN(kind=RestorePoint)`, decrements `pin_count`, and recomputes branch `restore_point_pin`.**
- **Empty recomputed restore point pins clear `branches_restore_point_pin_key`.** Do not write a zero sentinel because it blocks later `MutationType::ByteMin` initialization.
- **Snapshot selector resolution returns `ResolvedRestoreTarget`.** Latest reads branch head metadata, timestamp reads unexpired `PITR_INTERVAL` rows, and restore point reads retained restore point records without VTX fallback.
- **Selector-based fork and restore derive from `ResolvedRestoreTarget.database_branch_id`.** The target can be an ancestor branch, not only the current DBPTR branch.
- **Restore point lifecycle code uses the conveyer facade pattern.** Keep `conveyer/restore_point.rs` as the public `Db` facade and put creation, deletion, restore, resolution, and recompute code under `conveyer/restore_point/*.rs`.
- **Restore-to-restore-point captures the undo commit before rollback, then swaps DBPTR and writes the undo restore point in one UDB transaction.**
- **Restore point resolution carries bucket fork caps into database branch ancestry.** Do not use recursive DBPTR resolution when resolving inherited restore points; direct-walk bucket parents so parent commits after `parent_versionstamp` stay unreachable.
- **Lex order = chronological order within a single branch's parent chain.** Across sibling branches, restore points are not orderable in any meaningful way.
- **Restore points are sender-scoped.** A caller resolving a restore point on another database's branch returns `BranchNotReachable`. Cross-database isolation is enforced at the engine edge, not in this package.

## What we don't import from prior art

Single-writer + no-local-file + lazy-read-only constraints rule out most of the multi-writer machinery in mvSQLite and the local-file path in LiteFS / libSQL / DO SQLite. We import:

- LTX V3 file format (Litestream / LiteFS).
- Layer model: delta + image (Neon).
- Branch-as-pointer + branch-as-restore (Neon).
- Dependency-graph GC (Neon issue #707 cautionary tale).
- `Pos{TXID, PostApplyChecksum}` rolling checksum (LiteFS / Litestream).
- RestorePoint-as-time-token concept (CF DO).
- HWM pending markers (LiteFS).
- "Snapshot when log >= db size" image-rebuild rule (CF DO SRS).

We explicitly do **not** import:

- mvSQLite PLCC / DLCC / MPC / versionstamps / content-addressed dedup (single-writer).
- LiteFS / libSQL local SQLite file (no local files).
- LiteFS / DO multi-replica WAL stream (FDB durability replaces it).
- CF DO 3-of-5 follower quorum (FDB durability replaces it).
- Hydration-at-database-open (lazy read only).
- WAL-frame-level shipping (per-commit granularity).

## Errors

- All failable functions return `anyhow::Error`. Use `.context(...)` instead of `anyhow!`.
- Public error variants on this package's surface are `RivetError`-derived (`SqliteStorageError::*`).
- Keep `SqliteStorageError` downcastable with a manual `Display`/`Error` impl when using `RivetError` derive; envoy and VFS inspect typed variants.
- Quota cap rejection uses `SqliteStorageQuotaExceeded { remaining_bytes, payload_size }` mirroring database KV's shape.
- RestorePoint-out-of-retention returns `RestoreTargetExpired`; restore_point on unreachable branch returns `BranchNotReachable`; fork at GC'd point returns `ForkOutOfRetention`; deeper than `MAX_FORK_DEPTH` returns `ForkChainTooDeep`.

## Testing

- All test bodies live under `engine/packages/depot/tests/`. Source files may keep only tiny `#[cfg(test)] #[path = "..."] mod tests;` shims for private access.
- Tests run against real UDB via `test_db()` (RocksDB-backed temp instance). No mocks for storage paths.
- Shared depot integration-test helpers live in `tests/common/mod.rs`; use them for temp UDB creation, memory UPS construction, `Db` construction, and raw key reads instead of redefining helpers per test file.
- UPS dispatch tests use the UPS memory driver.
- Workflow compaction tests using real `Db::commit` should assert versionstamp-independent invariants; real UDB versionstamps do not encode txid bytes.
- Workflow force-compaction tests should wait for manager companion workflow ids before signaling so the manager is in its durable loop.
- Workflow compaction race tests can use debug-only workflow `test_hooks`; use stored `Notify` permits with `notify_one()` when a notification may arrive before the waiter arms.
- Workflow compaction skeleton tests should use `BumpSubSubject::WorkflowCreated { tag }` for workflow-row waits; keep `wait_until` for observations without notification hooks.
- Crash recovery tests use `checkpoint_test_db()` + `reopen_test_db()` for real persisted-restart state.
- Failure-injection tests use `MemoryStore::snapshot()`. The `fail_after_ops` budget keeps decrementing past the first injected error.
- Shared test error helpers should search `anyhow::Error::chain()` for typed `SqliteStorageError` causes so wrapped context does not hide the expected variant.
- Lease-expiry and time-window tests use `tokio::time::pause()` + `advance()` for determinism.
- Use a nil bucket `Db` to exercise branch-scoped hot compaction through public `compact_default_batch`.
- Latency tests that depend on `UDB_SIMULATED_LATENCY_MS` must live in a dedicated integration test binary because UDB caches the env var once per process via `OnceLock`.
- SQLite VFS integration and fault-injection tests live in `engine/packages/depot-client/` so they exercise the full VFS.
- Depot fault-injection APIs live only behind `depot/test-faults`; enable the feature from dev/test dependencies only.
- Production fault-leak checks run through `engine/packages/depot/scripts/check-production-fault-leaks.sh`.
- Depot fault-controller tests live in `tests/fault_controller.rs` and run with `cargo test -p depot --features test-faults --test fault_controller`.
- Commit fault-hook tests should search the `anyhow` error chain because UDB transaction failures wrap injected fault errors.

## Metrics

- All depot Prometheus metrics live in the single flat `depot::metrics` module. Do not add per-module or hierarchical `metrics.rs` files.
- Live-layer metrics (`sqlite_conveyer_*`, `sqlite_shard_cache_*`, `sqlite_branch_*`, `sqlite_restore_point_*`) carry a `node_id` label. Background-layer compaction metrics (`sqlite_compaction_*`) run on workflow workers with no node and omit `node_id`; keep them low-cardinality (`kind`, `result`, `tier`, `phase` only, no branch/database/actor ids).
- Record compaction pass outcomes from the `#[activity]` bodies (never inside `#[workflow]` fns), using the `metrics::record_*` helpers.
- Hot staging and hot install are separate pass kinds and separate throttle kinds (`hot_stage`, `hot_install`). Both charge the same write axis, so a merged `hot` kind cannot attribute a spent budget to either half.
- Hot fold volume carries a `destination` label (`staging` / `shard`) because a direct-to-shard fold stages nothing, so an unlabelled `hot_staged_bytes_total` would claim a staging write that never happened. Write amplification is `sqlite_compaction_hot_install_copied_bytes_total` over the fold bytes, never installed-over-staged: install reports what it published, copied or adopted in place, so those two are equal in both modes and their ratio measures nothing.
